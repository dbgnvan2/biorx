## Verification by construction (caller checklist a–f)

### (a) Faithful old-schema rebuild preserves everything — PASS

Built a database exactly as the pre-N1 code left it: `CREATE TABLE papers` with
`doi TEXT UNIQUE NOT NULL` + 12 historical `ALTER TABLE ADD COLUMN` calls, 2700
rows, summaries and bookmarks referencing paper ids, three middle rows and the
top row deleted (non-contiguous AUTOINCREMENT, high-water mark 2700). Ran
`Database(path)` and compared **every column of every row** before/after (all 22
columns, not the 6 the unit test samples):

- 2696/2696 rows byte-identical, ordered by id.
- `sqlite_sequence` for papers = 2700 after migration (was 2700) — the high-water
  mark survived the DROP/RENAME.
- summaries (→ paper 10) and bookmarks (→ paper 20) still join to the right titles.
- a post-migration insert got id 2701 (> old high-water mark; no id reuse).
- `doi` column `notnull` = 0 after migration.
- `idx_papers_canonical_id` unique index present.

Note: SQLite re-serializes `sqlite_master.sql` on every `ALTER TABLE ADD COLUMN`
(verified), and strips `IF NOT EXISTS` from the stored text (verified). So the
migration's "read CREATE statement back and rewrite it" approach does carry every
migration-added column in the real old database — the two facts the rewrite
depends on are both true.

### (b) Attempts to lose data or leave a half-migrated schema — PASS

- **Interrupt mid-rebuild** (monkeypatch `_verify_rebuild_counts` to raise):
  transaction rolls back; `papers` intact, `papers_rebuild` gone, `doi` still
  NOT NULL, 46/46 rows. No half-migrated schema.
- **`doi` in a different form** (`doi TEXT NOT NULL UNIQUE`): `RuntimeError`
  raised, table untouched, still NOT NULL. Refuses rather than guesses.
- **Quoted identifiers**: `"doi" TEXT UNIQUE NOT NULL` → refuses (regex does not
  match the quoted column); quoted table name only → migrates cleanly
  (doi notnull=0, row preserved).
- **Table with a trigger** (b3) / **extra index** (b4): rows preserved (46/46),
  but the trigger and the explicit index are **silently dropped** by the
  DROP+RENAME — see finding F1.
- **WAL-mode database**: rows preserved, doi made nullable.
- **Another connection open during migration**: rows preserved, second connection
  reads fine after.

### (c) Foreign keys and indexes across DROP/RENAME — PASS

`PRAGMA foreign_key_check` on summaries/bookmarks returns empty after migration;
no orphaned child rows. The migration's own connection has `foreign_keys=0`
(verified — the code never enables it), which is why `DROP TABLE papers` does not
fail or cascade and why the rename leaves the `REFERENCES papers(id)` clauses
valid. The `doi` UNIQUE auto-index is recreated from the rewritten CREATE
statement (doi dedup still enforced — see (d)); the canonical_id index is created
after the rebuild. Only paper-table *explicit* indexes/triggers are lost (F1).

## FINDINGS

F1 · P12/P2 · src/db.py::_relax_doi_not_null · LOW (out of blast radius)
  The rebuild is DROP TABLE + RENAME, which silently drops any **trigger, explicit
  index, or view** on `papers`. Proven by construction (b3/b4): rows survive, the
  objects do not, and nothing logs their loss. For THIS repo this is safe — grep
  finds zero `TRIGGER` statements and no explicit `CREATE INDEX` on `papers` (only
  `idx_usage_user_created` on usage_events and the post-rebuild
  `idx_papers_canonical_id`), so no real database has such an object to lose. The
  docstring says "every column … is carried across" but is silent about
  indexes/triggers/views. Recommend: a guard that refuses (or at least warns) when
  `sqlite_master` shows triggers/indexes on `papers`, or a docstring note. Not
  blocking for the current schema.

F2 · P8/P33 · INFO — no action
  The migration's own safety net compares row **counts** only; content equality is
  proven by the unit test (6 columns) and by this sweep's battery (all columns).
  Count + single transaction is an acceptable guard for an atomic rebuild; the
  stronger proof lives in the tests.

F3 · INFO — latent, no action
  The migration works because its connection runs with `foreign_keys=OFF`. If FK
  enforcement were ever enabled, `DROP TABLE papers` would raise (rollback, not
  data loss) — a safe failure, but worth knowing.
